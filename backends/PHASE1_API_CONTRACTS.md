# JobHub Phase 1 — REST and Socket.IO API contract inventory

This inventory is generated by scanning the actual route definitions in the patched JobHub source. The 60 currently mounted REST endpoints below include one new refresh route; all pre-existing REST paths are retained for compatibility. The new Stripe webhook route is separately mounted.

## Base URL and response envelope

- Development example: `http://localhost:3001/api/v1`. Production hostname comes from your API deployment.
- Common responses follow `{code, status, message, data}` (older endpoints may also expose pagination inside `data`).
- Authenticated routes require `Authorization: Bearer <accessToken>`; the new access token expires after 15 minutes. The new 30-day refresh token exists **only** in the `HttpOnly` `jobhub_refresh` cookie. The browser must use `credentials: "include"` and a configured trusted frontend origin.
- `POST /api/v1/auth/refresh` reads and atomically rotates that cookie; response includes `data.accessToken` and `data.user`. `POST /api/v1/auth/logout` revokes it and clears the cookie. The access token is never sent in the refresh-cookie body.
- New `POST /api/v1/stripe/webhook` is public only to **Stripe requests with a verified signature**; configure `STRIPE_WEBHOOK_SECRET` and deliver raw JSON. Client success redirects do not unlock payments.
- Role checks are server-controlled: self-service users may register only `seeker` or `recruiter`, with admin accounts provisioned using a trusted administrative workflow outside public registration.

## Secure resource semantics

- Job write operations: only the `author` recruiter. Deletions are soft-deletions. Public reads omit inactive, deleted and expired jobs.
- Applications: only the applicant can submit or withdraw; only the corresponding recruiter (or admin, if explicitly enabled) can review status. Public clients cannot set payment amounts.
- Interviews: only the job-owning recruiter can schedule, reschedule, change status or hire an eligible applicant.
- Companies and seeker profiles: editable only through the authenticated owner's routes; public candidate listings redact email, phone and resume.
- Conversations: a user must be a participant and must have a qualifying job application to initiate a new recruiter-candidate conversation. A conversation's Delete operation hides it from its requester, not both users.
- Messages: sender can edit/delete; receiver can mark read. Reading requires conversation membership.
- Stripe: `POST /stripe/create-checkout-session` accepts an **existing applicant-owned `applicationId` only**; the price comes from the server's `APPLICATION_BOOST_PRICE_CENTS`. `GET /stripe/payment-details/:sessionId` requires payer ownership or administrator role.
- Search endpoints: limits are bounded (typically maximum 50 records per query), text regex is escaped and queries are cached with time-limited Redis entries.

## Socket.IO contract

Connect to the backend's Socket.IO server with the short-lived JWT in `handshake.auth.token`. The socket middleware verifies user/session on connection and checks the session on each incoming event. The per-user room is `user:{userId}`; conversation room is `conversation:{conversationId}`.

| Client sends | Typical payload | Authorization / behavior |
|---|---|---|
| `conversations:get` | `{search?}` | Own conversations only |
| `conversation:join` | `{conversationId}` | Participant required |
| `conversation:leave` | `{conversationId}` | Leaves only own room |
| `messages:get` | `{conversationId,page?,limit?}` | Participant required before cache is read |
| `message:send` | `{conversationId,receiverId,content}` | Sender derived from token; receiver must be other participant |
| `message:edit` | `{messageId,content,conversationId?}` | Sender only |
| `message:delete` | `{messageId,conversationId?}` | Sender only |
| `message:read` | `{messageId,conversationId?}` | Receiver only |
| `notifications:get` | `{page?,limit?}` | Own notifications |
| `notification:read` | `{notificationId}` | Own notification |
| `notification:readAll` | `{}` | Own notifications |
| `notification:delete` | `{notificationId}` | Own notification |

Emitted events include `conversations:loaded`, `messages:loaded`, `message:new`, `message:edited`, `message:deleted`, `message:read`, `notifications:loaded`, `notification:new`, `notification:updated`, `notification:deleted`, `notifications:allRead` and `socket:error`.

## API minimization policy

Avoid creating redundant per-role aliases. Keep current routes as compatibility contracts during Phase 1. Prefer one filtered, paginated read of the right resource over fetching several pages for client-side filtering; reuse RTK Query cache and consolidate dashboard summary values when justified by actual network traces. Combining unrelated writes into one endpoint is *not* an optimization and would weaken authorization boundaries.

## Important caveats

This is a **route-level** source inventory, not a Swagger/OpenAPI specification, executable integration test, or proof of deployment health. Do not remove existing endpoints until their consumers are audited and migrated in a later phase.

**Public profile visibility:** the Phase 1 owner-visibility filter hides inactive/unverified account entries. If many profiles are disabled, list pages may contain fewer than their requested limit while legacy total counts still include those profiles; replace this with a database-level join before advertising accurate public totals at scale.
